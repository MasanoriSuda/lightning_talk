# 生成AIにるソフトウェアの設計

## 設計工程へのAI適用方針
- ソフトウェア設計とは
    - 「何を解くか」を定めた要求仕様をもとに、「どのようにして解くか」のレベルまで具体化し、実装工程へのスムーズな移行を目指す・
- 設計文章
    - 設計判断の経緯や結果をステークスホルダに伝えるためのコミュニケーション媒体。
        - 図、表、自然言語、数理的な形式記述など。
## 生成AI適用の課題と方針
- 設計工程においては、人間が主な作業者となり、一部の小さな作業を生成AIに代替・支援させるような適用方針がふさわしい。
    - 文献も非常に少ない
1. 支援、代替させる作業に必要な文脈情報を
2. 他の不要な情報を省きつつ
3. いかに正確に理解させるか

## 設計書からの情報生成
- 設計書の読み込み
生成AIに、より上位文書を読み込ませる必要がある。
    - 読み込み：上位文書の読み込ませる際に、後続タスクの必要な程度、生成AIが記述内容を理解できるように加工・修正して与えること。
    - 生成AIに読みやすい設計書
        - 人間がチェックしやすい設計書であることも兼ねる
    - テキストマークアップ言語
        - 生成AIが学習済みの機能(XMLなどのケースでは)を用いる
        - 図をマークアップで記述する
            - PlantUML
            - Marmaid形式
        - 表：行、列の見出しがどこか、データ部分がどこかわかりやすくする
        - DB設計でも意識する
        - 表データの「テキストとしての自然さ」は、続く応答の品質に影響する。
            - 人間が理解できないような入力まではしなくてよい、読み込み時に前処理などを行うと良い
 ## 複雑な文書の読み込み
 - LLMが読みやすい設計書フォーマットで書くことが望ましい、以下の場合はデータの前処理、読み込み方の指示を行う
     - 保守、流用開発で既存の設計文書を読むとき
     - 人間にとっての利便性を優先する場合  
     - 例：CSV->JSONにすることで生成AIの可読性が上がる

## レビュー
記載内容のレビュー。
文章を誤解なく理解してもらえるようにする。
「あいまいな表現の指摘」「矛盾の指摘」をしてもらう。（何を持ってあいまいかなどは別途指示を与える）
考慮できてない暗黙の条件の発見を行える。

## 設計書のドラフト作成
要求から設計書全体を高品質で作る事例はないのであくまで例。
自動可能な部分、人間がやらなければならない部分がある。
### 設計書作成の手順
要求定義をもとに基本設計、詳細設計を作成する。
プロジェクトによって異なるので、文書体系は考える。
①生成AI地震に要求〜詳細設計までの各工程の説明、定義を行わせる。各工程の入力、工程間でなにが具体化されどのように設計判断を行わなければならないか決定する。
②②で定義した工程の情報とシステムの概要を与え、基本設計書の雛形、章、節文章を提案させる。各章で用いる図、表をリストアップさせる。
③②で生成させた設計書の雛形、要求定義書を与えて、各章を順序よく生成する。コンテキストによってやりかたは変える。
④作成した設計書をブラッシュアップさせる。


### 設計工程の意識合わせと目次づくり
ユーザの想定する設計工程と、生成AIの出力する工程の定義をすり合わせる。
自分の想定する、基本設計書煮含めるべき内容とのギャプを修正する。

### 設計の具体化とドラフトの記述
実際に設計判断を行い、設計書を作成させる。
人間の知識や判断を要する工程がある（暗黙知などがあるため）
あらかじめ決まった文書体系に基づき、どのようなカテゴリ、章節構造の設計書を用意すればよいかが決まっている場合や設計書の作成要項がある場合、積極的に活用する。
既存のテンプレートがある場合、生成AIに提示するとよい。

### 設計書内に挿入する図の生成
図を作図させる、以下を意識するとよいかも
①作図可能化の判断
②より小さい独立した複数の図（部分図）に分割できるかの判断
③含めるべき部分図の一覧を予め出力させ、部分図を１ずつ生成させる。
