## バイブコーディングとは

> **"I just see things, say things, run things, and copy paste things, and it mostly works."**
> — Andrej Karpathy (2025)

- AIにコードを書かせ、人間はほとんどコードを読まない開発スタイル
- 「動けばOK」の精神で、雰囲気（vibes）に任せて進める
- プロトタイピングや個人開発では非常に高速

## バイブコーディングの課題

### バイブス（雰囲気）に任せてコードを書き、AIの出力が意図通りに動作すると盲信すること
- ナレッジ管理の欠如
- 出力のズレによる手戻り発生

大きな技術的負債となりうる（下手に動くのでタチがさらに悪い）

### AIがコードを書く時代に起きること
- 生成速度が上がる → 意思決定の記録が追いつかない
- 「なぜそう実装したか」がブラックボックス化
- 技術的負債に加えて理解負債という言葉が誕生

---

## Spec-Driven Development（SDD）とは？
AIが実行可能な明確なSpecを書くことが主要な成果物になるアプローチ

→ ハイプ・サイクルの **啓発期** に向かうための実践

最近だとKiroとかが流行っている。

２つの考え方の転換
- 開発の共通言語が「コード」から「自然言語」へ
- 人間は承認役、AIが開発の主体

---

### 原則
> **ドキュメントが正本。コードが矛盾したらドキュメントが勝つ。**

### 実践
- ドキュメント変更がアーキテクチャの Single Source of Truth
- コード変更は、まず仕様変更から始める
- AIもドキュメントに従う

---

## 責務境界を「禁止事項」で定義する

| 許可 | 禁止 |
|------|------|
| app → session | session → ai（直接呼び出し禁止）|
| app → ai | http → sip/rtp（触れてはいけない）|
| session → sip/rtp | media → 配信ロジック |

### なぜ禁止を明文化するか
- 「やっていいこと」より「やってはいけないこと」の方が明確
- レビューで「これはNG」と即判断できる
- AIにも境界を守らせられる

---

## AI分業：Claude Code vs Codex

| 観点 | Claude Code | Codex |
|------|-------------|-------|
| 担当 | 仕様/ドキュメント | 実装/テスト |
| 出力 | 仕様修正案、質問リスト | コード差分 |
| コード変更 | しない | する |
| 縛り | CLAUDE.md | AGENTS.md |

### ポイント
- **実装AIは仕様に従うだけ**
- 仕様を握る者がプロダクトを握る

---

## AGENTS.md：実装AIへの指示書

```markdown
## 依存方向（必須）
- app → session → (sip, rtp) → transport
- app → ai
- 禁止: session から ai 直呼び

## timeout/retry
- 外部 I/O は timeout 必須
- retry は ai モジュールに閉じ込める

## Backpressure（MVP）
- RTP → ASR: 最新優先（古い PCM 破棄）
- TTS → RTP: 割り込み優先
```

## チケットゲート：勝手に作らせない

### CLAUDE.md より

> 合意（チケット参照）が確認できない限り、作業を開始しないでください。

### 効果
- 「とりあえず作っちゃった」が防げる
- 意思決定の記録が必ず残る
- 後から「なぜこれがあるか」を追跡可能

## やってみてわかったこと

### 良かった点
- レビューが「仕様通りか」の確認に集中できる
- 新規参入者が docs からオンボーディングできる
- AIの出力品質が仕様の精度に比例するということがわかった

### 大変だった点
- 最初に docs を書く労力
- 「とりあえず動かしたい」誘惑との戦い(これは個人開発なのでよく負けてますが。。。)
- docs とコードの同期を保つ運用
- 自分で書いたわけではないので、承認作業が非常に大変

### 今後の課題
- AI要素技術に対する理解を更に深める
- コンテキスト管理、プロンプト設計の最適化
