|------|---------------|---------|
| 柔軟性 | 制約あり | 完全制御 |

## プロトコル層の責務分離

```
transport/  ← 生パケット I/O のみ（意味を持たない）
    │
sip/        ← SIP メッセージのパース・ビルド
rtp/        ← RTP パケット化、codec、ジッタバッファ
    │
session/    ← 呼制御、状態遷移（SIP/RTPの詳細を隠蔽）
    │
app/        ← ビジネスロジック（プロトコルを知らない）
```

### ルール
- 上位は下位のプロトコル詳細を知らない
- SIPヘッダ、RTP SSRC などは session より上に漏らさない

## 3. 音声認識（ASR）の仕組み

```
RTP受信 → μ-law decode → VAD → バッファ → WAV変換 → ASR → テキスト
  20ms        即時       RMS判定  発話単位    一括      API
```

### ポイント
- **20ms単位** で音声パケットが届き続ける
- 「いつ発話が終わったか」を検出する必要がある（VAD）
- 終わったら一括でASRに送る（バッチ方式）

---

## VAD（音声区間検出）

### RMSエネルギーで判定

```rust
fn rms_energy(payload: &[u8]) -> u32 {
    let sum: u64 = payload.iter()
        .map(|&b| mulaw_to_linear16(b) as i64)
        .map(|s| (s * s) as u64)
        .sum();
    ((sum / payload.len() as u64) as f64).sqrt() as u32
}
```

### 状態遷移
```
Idle ──(RMS ≧ 閾値)──► InSpeech ──(無音800ms)──► 発話終了
                           │
                      (最大30秒) ──► 強制終了
```

---

## VAD パラメータ

| パラメータ | 値 | 意味 |
|-----------|-----|------|
| `VAD_ENERGY_THRESHOLD` | 500 | 音声判定の閾値 |
| `VAD_END_SILENCE_MS` | 800ms | 無音継続で終了判定 |
| `VAD_MIN_SPEECH_MS` | 300ms | 最低発話長 |
| `VAD_MAX_SPEECH_MS` | 30,000ms | 最大発話長 |

### チューニングポイント
- 閾値低すぎ → ノイズ拾う
- 閾値高すぎ → 小声を逃す
- 無音判定短すぎ → 途中で切れる

## ASRサービス構成（2段フォールバック）

```
         ┌─────────────────┐
         │  AWS Transcribe │ ← 優先（精度高い）
```

## インテント分類のプロンプト

```rust
const DEFAULT_INTENT_PROMPT: &str = r#"
あなたはボイスボットの意図分類器です。
必ずJSONのみで分類してください。

形式: {"intent":"identity|weather|transfer|general_chat",
       "query":"<発話>","params":{...}}

- identity: 「誰ですか」「名前は」
- weather: 「天気」→ params に location
- transfer: 「転送して」「人に代わって」
- general_chat: それ以外
"#;
```

### ポイント
- LLMにJSON出力を強制 → パース可能
- 意図ごとに専用処理へルーティング

## なぜルールベースか

### LLMに全部任せない理由

| 全部LLM | インテント分類 |
|---------|---------------|
| 毎回重いLLM呼び出し | 軽いLLMで振り分け |
| 応答が不安定 | 処理が決定的 |
| コスト高い | 専用処理は安い |

### 例：天気
```
「東京の天気」
    ↓ intent: weather, location: 東京
    ↓ 気象庁API呼び出し（LLM不要）
    ↓ 結果をLLMで要約（1文）
    ↓ 「東京は晴れ、最高気温15度です」
```

## 5. LLM：Gemini + Ollama フォールバック

```
ユーザー質問
    ↓
┌─────────────────┐
│     Gemini      │ ← 優先（精度高い）
│ gemini-2.5-flash│
└────────┬────────┘
         │ エラー時
         ▼
┌─────────────────┐
│     Ollama      │ ← フォールバック（ローカル）
│   gemma3:4b     │
└────────┬────────┘
         │ それも失敗
         ▼
「すみません、うまく答えを用意できませんでした」
```

---

## LLM フォールバックの実装

```rust
pub async fn handle_user_question(
    messages: Vec<ChatMessage>,
) -> Result<String> {
    // 1. まず Gemini を試す
    match call_gemini(&messages).await {
        Ok(ans) => return Ok(ans),
        Err(e) => log::error!("Gemini failed: {e:?}")
    }
    // 2. 失敗したら Ollama
    match call_ollama(&messages).await {
        Ok(ans) => return Ok(ans),
        Err(e) => log::error!("Ollama failed: {e:?}")
    }
    // 3. 両方失敗したら謝罪
    Ok("すみません、うまく答えを用意できませんでした".into())
}
```

## 6. 設計の工夫

### なぜRustか

| 要件 | Rustの強み |
|------|-----------|
| 低レイテンシ | GCなし、予測可能 |
| 並行処理 | Tokio による軽量タスク |
| 安全性 | メモリ安全、データ競合防止 |
| 長時間運用 | メモリリークしにくい |

### 他の選択肢を選ばなかった理由
- Go: GCの停止時間
- C++: メモリ管理の事故リスク
- Python: レイテンシ

---

## 1セッション = 1タスク

```rust
tokio::spawn(async move {
    let session = Session::new(call_id);
    session.run().await;  // 通話終了まで生存
});
```

### メリット
- セッション間で状態を共有しない → ロック競合なし
- 1セッション死んでも他に影響しない
- スケールしやすい

## Backpressure 戦略

### 問題：処理が追いつかないとき何を捨てるか

| 箇所 | 戦略 | 理由 |
|------|------|------|
| RTP → ASR | **最新優先** | 遅延より鮮度 |
| TTS → RTP | **割り込み優先** | ユーザー発話で即停止 |
| LLM | **同時実行1** | リソース保護 |

```rust
// 古いデータを捨てて最新を優先
while let Ok(newer) = rx.try_recv() {
    current = newer;
}
process(current).await;
```

## MCP で何が変わるか

### Before（現状）
- 天気API呼び出しをハードコード
- 新しい機能追加 = コード変更

### After（MCP適用後）
- ツールをMCPサーバーとして外部化
- LLMが必要に応じてツールを呼び出し
- 新機能 = MCPサーバー追加（コード変更不要）

### 例
```json
{ "tool": "check_inventory",
  "params": { "product_id": "ABC123" } }
```
