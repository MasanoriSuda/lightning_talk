# 指示プロンプト開発の基礎
- 3.1 前提となるリファレンス
モデルがリリースされるたびに指示プロンプトのガイドが公開される。
モデル固有の性質を鑑みた指示スべき内容も公開されていることもある。
追加でガイドを参照することを推奨。

- 3.2 指示プロンプト開発時に把握しておくべき全体指針
指示プロンプト＝LLMの挙動制御ならびに挙動設計書

- 3.2.1 曖昧語の排除、具体性・再現性の確保
情報を具体化する。
「なるべく」「できるだけ」「ちゃんと」などのあいまいな言葉は避ける。
背景、やってほしいこと、制約出力形式が文中に散らばっていないかを確認する。

Markdown気泡を用いながら構造化したり、箇条書きを積極的に活用して可読性を高めたりすることで自由記述部分をなるべく無くすことを意識する。

- 3.2.2 英語の使用
制約、禁止事項
関数名や変数名
IT固有用語
JSON出力時のキー名
XMLタグ
条件分岐・繰り返し記述

3.2.3 否定形を避ける
「Aを選ばないで」より「Aを選ぶことは禁止されています」のほうがLLMは理解しやすい。
記載位置を上位にしたり、「A以外を選んでください（Aを選ぶことは禁止）」のように少し冗長性をもたせる、英語を使用するなども有効。

3.2.4 指示を矛盾させない
矛盾チェックのようなわかりやすい項目はLLMにプロンプトを確認させる工程を設け、事前に検知刷るような仕組みづくりをする。
参考情報などで矛盾が生じる可能性がある(RAGなど)
指示プロンプトで古い情報が混ざる可能性を教える、最新の情報を追加、日付などのメタデータを含めるのもよい。
ユーザーからの指示をシステムロールにいれて矛盾する。
指示プロンプトにユーザーがコントロールできるテキストは入れないようにする。

3.2.5 複数項目の指示・出力はなるべきさける
マルチタスクよりもシングルタスクが得意
並列に実行させると遂行度があがる、待ち時間もへる。

3.2.6 重要な情報は冒頭に書く
指示プロンプトにおいては特に先頭が重要な情報と認識する。

3.2.7 HowよりもWhatを重視する
イメージするタスクに関して細部まで言語化し、できるだけゴールに関する情報を与える。
ユーザーからコンテキストを引き出すための指示も重要。

# 3.4 指示プロンプトの基本構造
観点の整理
- 3.4.1 Role
具体的な職業名、役割、所属、「優秀」などのポジティなキーワドを入れることを推奨する。
- 3.4.2 Task
目的背景：なぜこのタスクを実行するのか
スコープ：タスクの範囲や選択（やってはいけないことを含む）
手順、チェックポイント：タスクを遂行するための具体的なステップや達成されるべきこと
完了条件：完了とみなされる条件
- 3.4.3 Input
入力に対して解説を与える
- 3.4.4 Output Fromat
JSON, YAMLなどLLMが出力するデータの構造を定義する
- 3.4.5 Guidelines 
タスクのルールや諸注意を記載する。
入力項目が多くなりすぎてコスト面やタスク精度に悪影響が出ることがあるので注意。
- 3.4.6 Prohibited Actions
禁止事項を書く。（推測で書くのを禁止するなど）
一般的に禁止事項は管理重要度が高い場合が多いのですべての項目で禁止である旨を繰り返し書いて強調するのも良い。
- 3.4.7. Timestamp、User Informationなど
情報探索の場合に最新の情報化把握するために使ったり、ユーザーの情報を聞く手間などを省く。
聞く必要がないがタスク遂行に必要な情報は、なるべくコンテキストに取り込んだほうが良い。
- 3.4.8 Knowledge Base
LLMが常に参照すべき情報を与える。
問い合わせ頻度の高いものは検索エンジンに問い合わせるよりも、あらかじめいれておくほうが効率的。
- 3.4.9 Example
例示、ふるまいの制御に非常に有効。

# 3.6 指示プロンプトの精度向上の技法
- 3.6.1 Few-Shot Prompting
指示プロンプトのExempleとして与えるパターン
APIに与える対話履歴の形式で例示するパターン
- Few-Shotにおける注意点
レジへのオーバーフィッティング、与えた例に過度に追従してしまうことがある。
- Few-Shot promptingと教師ありファインチューニングの違い
    Few-Shot Prompptとファインチューニングの比較
    - Few-Shot Promppting 
        少量の例をコンテキストに含めるのみ
        1ケースにおける追加コストは推論時のトークン消費のみ
        もともと学習されていないタスクはいくら例示しても意味がないことがある
    - フェ員チューニング
        モデルの再学習がプロセスが必要で、正門的な知識が求められる
        多数の質の高い学習データセットの準備の人的コスト
        モデルの学習時コスト
        APIによって別途コンピューティング費用
        モデルの内部パラメータが調整されるため、本来対応できないタスクが可能になることがある
- 以下の手法もあるが、プロンプト改善やRAGより先に検討されることはない
    - Direct Preference Optimization(DPO)
        - 複数回答の中から良い方法をえらぶ
    - Reinforcement Fine-tuning(FRT)
        - Reasonningモデルの思考過程を改善する
- 3.6.2 モデルから得るコンテキストを活用するChain of Thought
思考過程をレジスすることでLLMの論理的推論能力を高める手法。
「開放の探索空間を狭め、誤りの混入を減らす」ことで性能向上が見られる
- CoTの応用
    - 論理の構成
    - LLM内部知識の活用
    - 再帰修正
    - 指示のRecall
    - Structured Outputを活用したCoTの実装
